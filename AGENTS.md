# AGENTS.md — cpa-tea-plugins

Plugin suite for **CLIProxyAPI (CPA)**, upstream `router-for-me/CLIProxyAPI`.
Each plugin is a native Go `c-shared` library loaded by an **unmodified** CPA server.

**The point of this repo is that we do not fork CPA.** Our behaviour ships as plugins, so upstream
updates are someone else's problem. Protect that: if a feature seems to need a CPA patch, stop and
re-examine the plugin API before touching a fork.

## Repository

- GitHub: `the-tea-team/cpa-tea-plugins` — always pass `-R the-tea-team/cpa-tea-plugins` to `gh`.
- Default branch: `main`. Work lands there; PRs are for this repo only.
- Never open PRs or issues against `router-for-me/*` unless Kareem explicitly asks.
- Upstream CPA is a **read-only reference**. Keep a clone at `/root/reference/CLIProxyAPI` on
  kareem-dev for reading the real contracts — do not guess them from memory.
- Commit messages: Conventional Commits, human voice, no AI/process narration, no generated-by trailers.

## Layout rules

- **One plugin per directory** under `plugins/<id>/`. IDs are lowercase, hyphenated, and match the
  directory name (`tea-combos`, `tea-quota-router`). IDs must match CPA's rule
  `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`.
- **Every plugin is its own Go module** with its own `go.mod`, `go.sum`, `main.go`, `abi.go` and tests.
  No shared module across plugins: CPA loads each `.so` independently, and a plugin must build alone.
- **Shared code** goes in `internal/tea/` (a Go module plugins may `replace`-require locally), not by
  importing one plugin from another. Keep this rare — duplication between two plugins is cheaper than
  a coupling that forces them to release together.
- **`vendor/<id>/`** holds third-party plugins we adopt. Keep their original `LICENSE`, record the
  upstream repo and commit in `vendor/<id>/UPSTREAM.md`, and mark changes in their changelog.
- **`registry.json`** is generated by `scripts/registry-build.sh` from each plugin's `plugin.json`.
  Never hand-edit generated registry output; edit the plugin's own `plugin.json`.
- **Per-plugin metadata** lives in `plugins/<id>/plugin.json` (id, name, description, version, tags).
  The version there is the release version; keep it in sync with `main.go`'s `pluginVersion`.

## The CPA plugin contract (verified against v8.0.x)

A plugin exports a C ABI (`plugin.register`, `plugin.reconfigure`, `plugin.shutdown`) and returns a
`pluginapi.Plugin` whose `Capabilities` select which host interfaces it implements. Import
`github.com/router-for-me/CLIProxyAPI/v8/sdk/pluginapi` and `sdk/pluginabi`.

Capabilities you will actually use:

| Capability | Use for |
|---|---|
| `Scheduler` | Choosing a credential: `PickAuth` gets provider, model, candidates (ID, priority, status, attributes, metadata). Return an auth ID, or delegate to a built-in scheduler. This is where quota-aware RR lives. |
| `ModelRouter` | `RouteModel` sees source format, requested model, stream flag, headers, query, body, and available providers. Returns a provider + optional target model, or a plugin executor. |
| `Executor` | A plugin-owned upstream. Receives raw request, payload, headers and a `HostHTTPClient`. Required if a plugin must drive its own fallback chain. |
| `FrontendAuthProvider` | Authenticating inbound client keys before proxying. This is where named keys and per-key rules live. |
| `ManagementAPI` | Plugin-owned `/v0/management/...` endpoints plus `/v0/resource/plugins/<id>/` browser pages. Both CPA UIs add these to navigation automatically. |
| `QuotaProvider` | `DescribeQuota` / `FetchQuota` / `ResetQuota` for quota display and refresh. |

`Metadata.ConfigFields` describes plugin-owned config keys under `plugins.configs.<id>`, and CPA's UIs
render a generic settings form from them. Use it for simple scalar/list settings; ship a resource page
for anything structural (combo editors, key rule tables).

**Hard constraints**

- Build with `CGO_ENABLED=1` and `-buildmode=c-shared`. Plugins are `.so` (linux/freebsd), `.dylib`
  (darwin) or `.dll` (windows), and the build produces a `.h` you must delete.
- **CPA only discovers libraries in `<plugins.dir>/<goos>/<goarch>/` and `<plugins.dir>/`** — not in
  per-plugin subdirectories. Dev and install layouts must place each `<id>.so` flat in that dir.
  Optional versioned filenames are `<id>-v<version>.so`.
- CPA **rejects a plugin that declares no capabilities** (`invalid metadata or no capabilities`), and
  registration requires non-empty name, version, author and repository. The scaffold therefore ships a
  no-op scheduler (`Handled: false`) so a fresh plugin registers cleanly before you write real logic.
- The registration payload is a flat **capability-flag struct**, not the `pluginapi.Capabilities`
  interfaces. Its JSON names must match CPA's `internal/pluginhost/rpc_schema.go`; the template's
  `abiCapabilities` mirrors it. Add a flag only when you also handle that method.
- Go version must satisfy CPA's `go.mod` (currently `go 1.26.x`). Check upstream before upgrading.
- Pin the CPA dependency to a released tag (`v8.0.x`), not a branch. Bump it deliberately, per plugin.
- A plugin must **fail closed on registration errors and fail open at runtime where the host expects
  it**: return errors from `register`/`reconfigure`, but never panic inside a hook — the host fuses
  (disables) a plugin that panics, which silently changes routing behaviour.
- Never log credentials, tokens, auth file contents or request bodies containing them.
- No `log.Fatal*` in plugin code; return errors and use logrus.
- Per upstream convention, keep comments in English.

## Commands

```bash
scripts/new-plugin.sh <id>          # scaffold plugins/<id> from the template
scripts/build.sh [id]               # build one or all plugins (c-shared, strips the .h)
scripts/test.sh [id]                # go test ./... per plugin
scripts/check.sh                    # fmt, vet, tests, registry validation — the CI gate
scripts/registry-build.sh           # regenerate registry.json from plugin.json files
scripts/dev-up.sh                   # local CPA instance with our plugins dir mounted (dev loop)
```

Per plugin, the equivalent raw commands are:

```bash
cd plugins/<id>
gofmt -w .
go test ./...
CGO_ENABLED=1 go build -trimpath -buildmode=c-shared -ldflags "-s -w" -o <id>.so .
rm -f <id>.h
```

## Definition of done for a plugin change

1. `gofmt` clean, `go vet` clean, `go test ./...` passing for that plugin.
2. It builds as `c-shared` and the `.h` is removed.
3. `plugin.json` version and `main.go` `pluginVersion` agree, and `registry.json` is regenerated.
4. Its README states the capabilities it uses, the config keys it owns, and its failure behaviour.
5. If it touches routing or auth, a test proves the decision for at least the empty-candidates case
   and the "no eligible credential" case.
6. `scripts/check.sh` passes before pushing.

## Technical findings

- **Combo fallback across models: solved, no core patch.** A plugin registers `ModelRouter` +
  `Executor`; the router sends the combo name to the plugin's own executor, which calls
  `host.model.execute` per member. Proven against a real CPA with a mock upstream. Read
  `spikes/tea-combo-spike/FINDINGS.md` before writing `tea-combos`. It lists seven traps, the worst
  being that an executor with no declared input/output formats is skipped silently.
- **Native alias pools already do RR + failover.** Repeating one `alias` in an upstream group's
  `models` makes a pool: one client-visible alias, requests round-robin across the listed upstreams,
  failures fall through to the next pool entry. Do not rebuild single-provider RR as a feature. Our
  gap is cross-provider combos, first-class named objects, runtime editing, and session affinity.
- **Plugin pages appear in CPA-Manager-Plus automatically** (verified against CPAMP `a67ed88`): return a
  `ResourceRoute` with a non-empty `Menu` from the `ManagementAPI` capability, set `Metadata.Logo`, keep
  the plugin enabled, and CPAMP renders a sidebar entry plus an iframe of that resource
  (`pluginResources.ts` -> `collectPluginResourceEntries`). No upstream change needed.
- **Resource routes are NOT management-authenticated.** `pluginResourceNoRoute` bypasses the management
  middleware, so a resource route may serve only a static shell; all data goes through authenticated
  `/v0/management/` routes. They also 404 when `home.enabled: true`.
- Streaming fallback is not proven and is only safe before the first byte is sent.
- Still unverified: whether scheduler candidate `Metadata` exposes per-credential quota, or quota must
  be fetched through `QuotaProvider` and joined by auth ID. Spike with real credentials.
